# Учебный конспект: разбор нативных библиотек (Go-cgo и C++/Djinni)

> Архивный учебный конспект. [Реверс установленной сборки](native_transport_reverse.md) подтверждает промежуточную роль `proxy.dll` и уточняет, какие ветви используют Titan и Go.

Методика, инструменты и архитектура — на примере опознанных `libgonet.dll` (Go) и
`libtitancpp.dll` (C++). Это учебный материал о **методе анализа**, а не реконструкция
протокола/крипто imo: до внутренностей хендшейка, ключей и формата кадров здесь намеренно
не идём.

## 0. Общий порядок анализа любой нативной DLL

1. **Триаж/паспорт:** архитектура, компилятор, упаковка, секции, импорты/экспорты.
   Инструменты: Detect It Easy (DIE), CFF Explorer, `dumpbin /headers /exports /imports`,
   `pefile` (Python).
2. **Строки и метаданные:** `strings`, поиск стампов тулчейна, версий, путей сборки.
3. **Статический дизассемблер/декомпилятор:** Ghidra (бесплатный), IDA, Binary Ninja.
4. **Восстановление символов/типов** — специфично для тулчейна (см. ниже).
5. **Динамика только на своём тестовом процессе, в ВМ/песочнице:** x64dbg, WinDbg,
   API Monitor, трассировка Frida своего же тестового процесса.
6. **Документирование графа вызовов** от экспортов вглубь.

Экспорт — это публичная граница (façade). С неё всегда и начинают: видно «что наружу»,
а внутренности читаются от этих точек входа.

## 1. Go-половина (`libgonet.dll`, Go 1.24.5, cgo)

### Как опознать Go-бинарь
- Стамп сборки `go1.NN`, секция `.go.buildinfo` (для `go version -m <file>`).
- Таблица `runtime.pclntab` — карта «адрес → имя функции», которую Go встраивает всегда.
  По ней восстанавливаются имена даже в «очищенном» бинаре.
- Масса символов `runtime.*`, `sync.*`, характерный аллокатор/планировщик.

### Инструменты восстановления
- **Mandiant GoReSym** — вытаскивает метаданные функций и типы из pclntab/moduledata.
- **Ghidra:** скрипты `AlphaGolang`, `golang_loader_assist`, встроенный Golang-анализатор
  в свежих версиях.
- **IDA:** `go_parser` / `golang_loader_assist`; `redress` как отдельная утилита.

### Что важно знать про cgo-экспорты
- `//export Name` в Go генерирует C-вызываемую обёртку; наружу идёт **cdecl C-ABI**.
  В `libgonet` это `gonet_init`, `gonet_new_tls/ws/hs/http`, `gonet_conn_connect/write/close`,
  `gonet_http_*`, `gonet_free/destroy`, плюс `_cgo_dummy_export`.
- Перед вызовом Go-рантайм должен быть инициализирован — это делает сам cgo-слой.
- Подводные камни чтения Go-кода: строка = (указатель, длина), **не** null-terminated;
  слайс = (ptr, len, cap); вызовы через интерфейсы идут через itable; свои соглашения о
  стеке/горутинах. Это главные отличия от «обычного» C при чтении декомпиляции.

### Архитектурный вывод
Чистый транспорт: поднять защищённый/обычный канал (`tls/ws/hs/http`) и гонять байты
(`conn_write`, `http_send`). Логики сообщений тут нет.

## 2. C++-половина (`libtitancpp.dll`, MSVC, Djinni)

### Демэнглинг имён
MSVC-имена вида `??0YYProtoX@bigo_protox_djinni@@QAE@XZ` раскручиваются:
- `undname.exe` (идёт с MSVC), `llvm-undname`, либо встроенно в IDA/Ghidra.
- Из них восстанавливаются класс, namespace, сигнатура (ctor/dtor/метод, аргументы).

### Паттерн Djinni (Dropbox)
- Djinni — генератор кросс-язычных биндингов: интерфейс описывается в `.djinni` IDL →
  генерируется C++-абстрактный класс + **CppProxy** + сторона другого языка
  (JNI/ObjC/кастомный мост). Namespace `*_djinni` и парные прокси-классы — его «подпись».
- Практический смысл для анализа: по этим интерфейсам видно, **какую поверхность C++-ядро
  отдаёт в managed-слой** (тот самый мост в `Imo.*`-сборки). То есть Djinni-граница — это
  карта «что managed-код может звать у нативного ядра».

### Восстановление классов C++
- Анализ **vtable + RTTI** (MSVC пишет RTTI): Ghidra-скрипты/плагины (class-informer в IDA,
  OOAnalyzer/`Recover C++ Class` в Ghidra) собирают иерархию классов из таблиц виртуальных
  функций.
- `bigo_protox` / `YYProtoX` — слой протокола ProtoX (сериализация/маршрутизация команд);
  на учебном уровне достаточно зафиксировать, что это **протокольный слой над транспортом
  libgonet**, не трогая внутреннюю схему кадров.

## 3. Архитектура imo-клиента (сводно, из façade-уровня)

```
WPF/.NET (Imo.Dispatcher, Imo.Message)      ← UI/view-models
        │  Djinni-мост
Imo.ChannelNetwork / Imo.DataCore (managed)  ← Market/NetMarket фасады
        │  Djinni-интерфейсы
libtitancpp.dll  (C++, bigo_protox / YYProtoX) ← протокол ProtoX
        │  C-ABI (gonet_*)
libgonet.dll     (Go 1.24.5, cgo)              ← транспорт TLS/WS/HTTP
        │
сеть → серверы imo
```

Каждый слой узнаётся по façade: managed-типы (reflection), C++-экспорты (демэнглинг),
Go-экспорты (cgo). Это и есть «скелет» для учёбы.

## 4. Правовая/этическая рамка (коротко)

- Реверс для **обучения и интероперабельности** во многих юрисдикциях допустим (например,
  в ЕС — исключение для интероперабельности в Директиве о ПО; в США — отдельные исключения
  DMCA §1201 для интеропа и security-research). Это не юридическая консультация.
- Граница — не в чтении бинаря, а в **применении**: воспроизведение закрытого протокола для
  неавторизованного клиента, обход защиты канала или нарушение ToS сервиса — отдельная история,
  и этот конспект туда не ведёт. Учимся на методе и архитектуре.

## 5. Нейтральные упражнения (без привязки к imo)

- Собрать свою Go-DLL с `//export` и `-buildmode=c-shared`, посмотреть, как выглядит
  pclntab и cgo-обёртки в Ghidra — отличный способ понять Go-RE на своём коде.
- Сгенерировать минимальный Djinni-интерфейс (C++ ↔ Java) и разобрать сгенерированные
  прокси — так паттерн becomes очевиден на дизассемблере.
